# Architecture

## Goal

Keep one always-available Codex environment in Azure without exposing an administrative port publicly, while preserving many Git repositories independently of VM replacement.

## Runtime and access

`scripts/codex-vm.sh` is the Mac operator's single front door and the repository's only production shell script. Its interactive menu, explicit subcommands, Terraform SSH-key bootstrap, and VM payloads are embedded in that file. For each action, the console materializes the required executable bundle in a private mode-0700 temporary root linked to the checkout's Terraform tree, preserves isolated traps and cross-calls, and removes the root afterward. Terraform remains an explicitly manual workflow outside the console. Interactive SSH always targets the private VPN address.

Terraform owns Azure infrastructure only. Before VM creation, its external data source invokes a private console entrypoint that creates or verifies the Mac Ed25519 pair and returns only the public key; private key bytes remain outside Terraform state. Terraform then creates the VM, network, managed disk, attachment, protection, backup, and non-secret outputs without custom data, cloud-init preparation, Terraform VM Run Command resources, or remote-exec. The console displays its menu before checking VM preparation. When the operator selects a dependent workflow, the console verifies through Azure Run Command that `/var/lib/codex-on-vm/prepared` matches the Terraform Codex version and projects mount. Missing, stale, unreadable, or unreachable preparation requires explicit confirmation before the idempotent setup workflow runs; declining cancels the selected action, and non-interactive commands fail with an explicit setup instruction. The embedded machine-preparation helper reads Terraform outputs, waits for the intended VM agent, and transmits checksummed VM payloads extracted from the same console file through Azure Run Command. It reads back the readiness marker and Ed25519 host key before it writes local SSH trust files.

The remotely invoked provisioner runs as Azure Run Command's root context, but installs and bootstraps Codex for `azureadmin`. It mounts and verifies the managed projects disk before installing the pinned CLI into a Codex home on that disk. It prefers an existing `/home/azureadmin/projects/dot-codex` checkout, otherwise initializes `/home/azureadmin/projects/.codex`, and exposes the selected directory through `/home/azureadmin/.codex`. The CLI publication also lives under the projects disk. Before daemon bootstrap, the provisioner installs `bubblewrap` and loads `bwrap-userns-restrict`. ChatGPT authentication and pairing remain separate post-deploy user actions launched by the console's `sign-in` and `pair` workflows, so credentials and short-lived codes never enter Terraform state or provider payloads.

Remote Control is the normal path after pairing. It uses the managed daemon and outbound connectivity, so neither the Codex app server nor an unauthenticated listener is exposed publicly. The official Codex manual describes `codex remote-control start` as starting the local daemon with Remote Control enabled and `codex remote-control pair` as producing a short-lived pairing code.

Codex's detached updater is not reboot-persistent, so the locally launched provisioner installs a systemd boot service that re-runs managed bootstrap as `azureadmin` and a one-minute timer that invokes the production health helper. Systemd is the only execution initiated by the VM after preparation; requiring the Mac to remain online would defeat reboot recovery. Both oneshot units use `KillMode=process` because Codex's supported lifecycle command deliberately leaves the standalone daemon running after its launcher exits. The helper accepts readiness only from a connected, non-timed-out machine-readable Remote Control result with an environment identity, while separately checking the local daemon. A healthy local daemon is left running through four consecutive relay failures; the fifth may restart it once, and continued failures use bounded exponential backoff. The helper signals a stale updater only when the daemon's PID records, process start times, user, exact updater command, defunct child state, and parent relationship all match; it never deletes authentication, pairing, or daemon settings.

The VM retains a Standard public IP for outbound connectivity and the self-hosted OpenVPN endpoint. The network security group has exactly one standing inbound rule: `AllowOpenVpn` permits UDP/1194 to the VM. TCP/22 is never exposed by Terraform or the operator console. From the Mac, setup and Remote Control recovery use [Azure Run Command](https://learn.microsoft.com/en-us/azure/virtual-machines/linux/run-command) through the VM agent. Direct SSH is available only at `10.250.0.1` after the Mac connects to OpenVPN. SSH allows only the generated Mac Ed25519 key, rejects passwords and root, and uses a host key captured through Azure Run Command.

Terraform owns the non-secret OpenVPN network contract, while `scripts/codex-vm.sh vpn-setup` owns secret reconciliation and deliberate rotation. Keeping that work outside Terraform and cloud-init prevents CA, client, server, and `tls-crypt` keys from entering Terraform state or replacement-time payloads. The helper first requires the existing tunnel, then copies only the server bundle through `codex-on-vm-vpn` and validates the native Ubuntu OpenVPN service. Server material persists on the managed projects disk and setup restores it into `/etc/openvpn/server` after VM replacement. The client profile is split-tunnel: it reaches only `10.250.0.0/24`, does not replace the Mac default route or DNS, and exposes no other VNet resources. Initial trust bootstrap without the existing Mac profile and persistent server bundle is intentionally outside this repository's supported workflow.

This design uses the free, self-hosted [OpenVPN Community Edition](https://openvpn.net/community/) on the already running VM. It deliberately avoids Azure VPN Gateway and Bastion resources; ordinary VM and bandwidth charges still apply. It is a single-client developer-access design, not a managed multi-user VPN service.

## Workspace storage decision

The live workspace is a 256 GiB Standard SSD managed disk attached at LUN 0 and formatted as ext4. The locally launched provisioner locates it through Azure's predictable `/dev/disk/azure/data/by-lun/0` link, creates a partition and filesystem only when the disk is blank, and persists the mount at `/home/azureadmin/projects` by UUID. Microsoft recommends stable Azure device links and UUID-based `/etc/fstab` entries because Linux device names can change across boots. See [Azure Linux VM utilities](https://learn.microsoft.com/en-us/azure/virtual-machines/linux/azure-virtual-machine-utilities) and [attach and mount a data disk](https://learn.microsoft.com/en-us/azure/virtual-machines/linux/attach-disk-portal).

This is the best default when the VM is the primary Git and build machine:

- A managed disk is block storage presented to one VM, so ext4 provides native Linux permissions, links, file locking, and low-latency metadata behavior. [Azure managed disk types](https://learn.microsoft.com/en-us/azure/virtual-machines/disks-types) include Standard SSD as the cost-sensitive general-purpose SSD tier.
- Git, package managers, language servers, and builds create many small metadata operations. Azure Files is a network filesystem, and Microsoft notes that metadata-heavy workloads are sensitive to metadata latency and that SMB metadata caching is a performance consideration. See [Azure Files performance](https://learn.microsoft.com/en-us/azure/storage/files/understand-performance) and [SMB performance](https://learn.microsoft.com/en-us/azure/storage/files/smb-performance).
- The disk is independent of the VM resource, denies public disk access, has an Azure `CanNotDelete` lock and Terraform `prevent_destroy`, and is included in [Azure VM backup](https://learn.microsoft.com/en-us/azure/backup/selective-disk-backup-restore).

Azure Files would be preferable if simultaneous first-class SMB mounts from multiple machines were the primary requirement. It is not selected because the VM is the source of truth for many active Git repositories. Premium SSD Azure Files with suitable provisioning and metadata caching could reduce latency, but it adds cost and still makes the live repository a shared network filesystem.

## Mac access

VS Code Remote-SSH should connect to the generated `codex-on-vm-vpn` alias while the Mac's OpenVPN client is connected. VS Code Server, Git, language servers, package managers, and builds then run against the native Linux filesystem on the VM. This is the preferred daily development model.

If high-performance Mac-native work becomes the main workflow, keep a separate Mac clone and synchronize through normal Git remotes. A managed disk cannot be attached as writable block storage to the Mac while it is attached to the VM.

## Persistence and failure boundaries

- Replacing the VM: the managed disk and its data survive, then Terraform reattaches it at LUN 0.
- Codex state during VM replacement: after Terraform reattaches the disk, the operator reruns `scripts/codex-vm.sh setup`. Systemd requires the projects mount; preparation selects the existing persistent Codex home, recreates `~/.codex` and `/usr/local/bin/codex`, and reuses authentication, configuration, sessions, skills, packages, and daemon state.
- Recreating all infrastructure: the disk destruction guard must be deliberately removed after a verified export; this prevents an ordinary destroy from silently erasing the repositories.
- Backup: the Recovery Services vault protects the VM with data-disk LUN 0 included and 30 daily recovery points. Configuration is not a restore test; operations still require a live restore drill.
- Existing Azure Files deployment: this code does not migrate it. Back up and verify the old share before applying a plan that removes it.
- OpenVPN service or OS-disk replacement: normal setup restores the last successful server bundle from the managed projects disk; deliberate trust rotation remains a separate Mac-owned operation.
- Remote Control failure: systemd performs boot and periodic recovery; Azure Run Command is the first operator recovery path, and OpenVPN SSH is the only direct-access path. The app-server itself is never opened as a public listener.
